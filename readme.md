# MoodFit — 내 옷장 기준으로 오늘 코디를 짜 주는 AI

> 쇼핑몰과 코디 커뮤니티는 **남의 코디**를 보여 주지만, "오늘 **내 옷장에 있는 옷으로** 뭘 입을지"는 정해 주지 않습니다.
> MoodFit은 날씨·일정·기분을 받아 내 옷 중에서 코디 3개를 고르고, 왜 그 조합인지 항목별 점수와 함께 보여 줍니다.
> 앱을 열면 그날 날씨로 첫 추천이 바로 뜹니다.

### 이 프로젝트에서 한 일

- **실제 옷장 사진에 AI 붙이기** — FashionCLIP으로 종류·계절·색·스타일 자동 분류. 상품 사진 벤치마크에서는 괜찮던 분류가
  **직접 찍은 옷 사진(개발용 15벌 · 시험용 9벌)에서는 무너지는 것**을 숫자로 확인했습니다. 특히 하의 계절은 8벌 중 4벌만 맞아서,
  약한 부분은 사용자에게 확인을 받고 **사용자가 고친 값은 AI가 다시 덮어쓰지 않게** 설계했습니다.
- **코디 조합 단위 추천** — 내 옷으로 만들 수 있는 조합을 모두 만들어 날씨 · 상황(사진 분석) · 색 조합 · 새로움 점수로 고르고,
  LLM은 고른 코디의 설명만 씁니다. 같은 조건이면 늘 같은 결과가 나오고, LLM이 실패해도 추천은 동작합니다.
- **정직한 평가** — 점수 구간을 섞어 뽑은 코디 36개를 직접 평가해 AUC를 쟀습니다. 전체 점수는 **0.58**(동전 던지기보다 조금 나은 수준),
  색 조합 규칙만 쓰면 **0.71**. 같은 평가로 가중치를 바꿔 숫자를 부풀리지 않고, 다음에 새 평가로 따로 검증할 계획을 적었습니다.
- **등록 부담 줄이기** — 기본 옷 44종 카탈로그. 쇼핑몰 크롤링 대신 사용이 허용된 **Pixabay API**로 사진을 모았습니다.
  처음엔 "AI 판정 42/44 통과"였지만 직접 보니 쓸 만한 사진은 5~6장뿐이었고, **상품 사진 · 사람 없음 · 종류 · 색 · 배경 제거 기준**을
  세워 통과한 사진만 쓰고 나머지는 그림으로 대체했습니다. 상품 링크 하나로 내 옷 사진을 가져오는 기능도 있습니다.
- **보안** — 비밀번호 해시 · JWT, API 키는 서버 환경변수에만, 상품 링크 가져오기의 **SSRF(서버가 내부망에 접속하게 만드는 공격) 차단**.

**범위와 한계** — 수백만 장의 코디 사진을 가진 쇼핑몰처럼 "남의 스타일 구경"은 목표가 아닙니다. 옷이 적으면 추천도 한정되고,
옷끼리의 격(포멀·캐주얼)을 맞추는 점수는 아직 없습니다. 자세한 건 [한계와 다음 단계](#한계와-다음-단계).

- 백엔드: **FastAPI** · SQLAlchemy(SQLite) · JWT 로그인 · Groq LLM · 기상청 단기예보 API(키가 없으면 Open-Meteo)
- AI: FashionCLIP 제로샷 + 로지스틱 회귀 probe(스타일), rembg 배경 제거 — 선택 설치
- 프론트엔드: HTML · CSS · JavaScript (빌드 도구 없이 FastAPI가 같이 서빙)
- 테스트: pytest **63개** (외부 API·모델 없이 실행)

| 상품 링크로 가져오기 | 산 옷의 상품 페이지 주소를 넣으면 그 페이지의 대표 사진·상품명을 읽어 와 AI가 나머지를 채움 |

| 배경 제거 | 집에서 찍은 사진의 바닥·손·옷걸이를 지우고 옷만 밝은 정사각형 배경에 올려 상품 사진처럼 표시 (rembg, 원본은 따로 보관) |
| 자동 이름 | "블랙 토트백", "네이비 와이드 팬츠"처럼 색 + 세부 종류로 이름을 제안 (직접 쓴 이름이 우선) |
| 옷 그림 | 사진이 없는 옷은 종류 모양 그림을 그 옷의 색으로 칠해 표시 (쇼핑몰 사진은 저작권 때문에 쓰지 않음) |

| 코디 평가 | 추천 코디와 평가용 코디에 👍/👎를 남기면 저장해, 점수가 내 취향과 맞는지 AUC로 측정 (`scripts/eval_outfits.py`) |
| 착용 기록 | "오늘 이거 입기"를 누르면 기록해, 다음 추천에서 최근 입은 옷이 덜 나오게 함 |

## 추천은 이렇게 동작합니다

처음 버전은 옷을 한 벌씩 따로 점수 매기고, 조합은 LLM이 골랐습니다. 그러면 색이 안 어울리는 조합이나 상황에 안 맞는 조합을 막을 수 없고,
"왜 이 조합인지"를 설명할 수 없었습니다. 그래서 **코디 조합 단위로 점수를 매기고, LLM은 설명만** 쓰도록 바꿨습니다.

```
날씨·기분·상황 선택
  → 내 옷으로 (상의, 하의, 아우터) 조합을 모두 만듦 (app/services/outfits.py)
       체감 17도 미만은 아우터 필수, 17~22도는 선택, 23도 이상은 제외. 가방은 색이 가장 잘 맞는 것 하나를 붙임
  → 조합마다 점수 (100점)
       날씨 35   옷마다 계절이 오늘 기온에 맞는지
       상황 30   FashionCLIP이 옷 사진을 보고 계산한 출근·데이트·운동… 적합도 (사진 없는 옷은 스타일 규칙)
       색 조합 20 뉴트럴 + 포인트 1색, 톤온톤, 포인트 색 2개 이상 감점, 블랙+네이비 감점, 청바지는 무채색 취급
       새로움 10 최근 3일 안에 입은 옷이 적을수록
       기분·스타일 5
  → 서로 겹치지 않는(상의·하의·아우터 중 2개 이상 같으면 제외) 상위 3개
  → LLM(Groq)에는 고른 코디와 규칙 이유를 주고 설명만 부탁. LLM이 실패해도 코디와 이유는 그대로 보여 줌
```

- 점수 계산에는 LLM이 끼지 않아서, 같은 조건이면 늘 같은 결과가 나오고 화면에 항목별 점수와 이유를 그대로 보여 줄 수 있습니다.
- 상황 적합도는 옷을 저장하거나 "다시 분석"할 때 미리 계산해 DB에 넣어 둡니다. 추천할 때는 모델을 돌리지 않아 빠릅니다.
- CLIP 확률은 옷마다 퍼진 정도가 달라서, **그 옷이 가장 어울리는 상황 대비 비율**로 바꿔 씁니다. (셔츠는 출근 1.0, 운동 0.1 같은 식)
- 옷이 많아도 조합 수가 폭발하지 않게 종류별로 개별 점수 상위 12벌만 조합합니다.
- 옷장에 상의·하의가 없으면 LLM이 일반적인 코디 조언을 줍니다.

### 추천이 맞는지 어떻게 재나 (`scripts/eval_outfits.py`)

추천 결과에 남긴 👍/👎만 모으면 이미 점수가 높은 코디만 평가하게 되어 비교가 안 됩니다. 그래서 화면에 **"🎲 코디 평가하기"**를 따로 두었습니다.

- 처음에는 완전 무작위 코디를 보여 줬는데, 직접 써 보니 대부분 엉뚱한 조합이라 평가하는 사람이 금방 지쳤습니다.
- 그래서 무작위 코디 30개를 점수 순으로 세우고 **상위 1/3에서 50%, 중간 30%, 하위 20%** 확률로 하나를 골라 보여 줍니다. 점수는 숨깁니다.
- 좋은 코디와 별로인 코디가 모두 섞여 들어오므로 "점수가 취향을 가르는지"를 잴 수 있습니다. 다만 상위 구간을 더 많이 보여 주므로, 결과는 "이 비율로 섞인 코디들 안에서의 정확도"로 읽어야 합니다.

이 평가로 다음을 잽니다.

- **AUC**: 좋아요 코디와 별로 코디를 하나씩 뽑았을 때 좋아요 쪽 점수가 더 높을 확률 (0.5 = 동전 던지기)
- 항목 하나씩만 / 하나씩 빼고 → 어떤 항목이 실제로 취향을 가르는지 (ablation)
- 평가로 가중치를 학습(로지스틱 회귀, leave-one-out) → 가중치를 내 취향에 맞추면 얼마나 나아지는지

- 평가로 가중치를 학습(로지스틱 회귀) → 반복 층화 교차검증으로, 학습에 안 쓴 평가로만 잽니다.
  처음엔 leave-one-out을 썼는데 AUC가 0.09로 비정상적으로 낮게 나왔습니다. 평가가 적고 좋아요가 드물면 하나를 뺄 때마다
  절편이 반대로 움직이는 LOO의 알려진 편향이라, 폴드마다 AUC를 재는 방식으로 바꿨습니다.

**1차 결과 (평가 36개: 좋아요 9 / 별로 27, 체감 0°C 출근 조건)**

| 방법 | AUC |
|---|---|
| 전체 점수 (지금 앱) | 0.58 |
| 색 조합만 | **0.71** |
| 상황(FashionCLIP)만 | 0.61 |
| 날씨만 | 0.43 |
| 기분·스타일만 | 0.33 |
| 평가로 가중치 학습 (3겹 교차검증 × 30번) | 0.49 |

- 전체 점수는 동전 던지기(0.5)보다 **조금 나은 수준**입니다. 아직 "추천이 취향을 잘 맞힌다"고 말할 수 없습니다.
- **색 조합 규칙이 취향을 가장 잘 갈랐고(0.71)**, 사진으로 계산한 상황 점수가 그다음(0.61)이었습니다.
- 날씨 점수는 평가가 모두 같은 날(0°C)에 모여 있어 옷마다 차이가 작아 판단할 수 없습니다.
- 기분·스타일 점수는 오히려 반대(0.33)였습니다. 자동으로 붙인 스타일 라벨이 부정확하거나, 기본 조건(편안함·캐주얼)이 실제 취향과 다를 수 있습니다.
- 가중치를 평가로 학습해도 0.49로 나아지지 않았습니다. 36개로는 학습하기에 부족합니다.
- 그래서 **같은 평가로 가중치를 바꾸고 다시 재지 않았습니다**(그러면 점수가 과대평가됨). 다음 단계는 색 비중을 올리고 스타일 비중을 내린 버전을 정해 두고, **새로 모은 평가로 따로 검증**하는 것입니다. 평가가 수십 개 수준이면 AUC가 0.05~0.1씩 흔들릴 수 있습니다.

## 옷을 하나씩 찍어 올리지 않아도 되게

직접 써 보니 가장 큰 문제는 **옷을 한 벌씩 찍어 올려야 시작할 수 있다**는 점이었습니다. 코디가 어려운 사람일수록 여기서 그만둡니다.

**1. 기본 옷으로 채우기 (사진 없이 시작)** — `scripts/build_catalog.py`, `app/services/catalog.py`

- 흰 티, 청바지, 검정 슬랙스, 트렌치코트처럼 흔히 가진 기본 아이템 44종을 정해 두고, 가진 것과 비슷한 걸 누르기만 하면 옷장에 들어갑니다.
- 사진은 **쇼핑몰을 크롤링하지 않고 무료 사진 API(Pixabay)**로 모았습니다. 쇼핑몰 상품 사진은 저작권과 이용약관(자동 수집 금지) 문제가 있어 공개 포트폴리오에 쓸 수 없지만, Pixabay API는 프로그램 사용을 허용하고 사진을 내 서버에 내려받아 쓰도록 안내합니다(원래 주소를 계속 띄우는 핫링크는 금지). 'fashion' 분류로 먼저 거릅니다.
- 처음에는 Pexels API로 만들었는데, 2026년 11월 현재 새 키 발급이 중단돼 있어 Pixabay를 기본으로 하고 Pexels도 쓸 수 있게 두었습니다.
- **처음 방식과 실패**: 검색 후보 중 "상품 사진다움 × 종류가 맞을 확률"이 가장 높은 사진을 고르고 AI로 종류를 다시 확인했더니 **44개 중 42개가 '맞음'**이었습니다. 그런데 사진을 직접 보니 쓸 만한 건 5~6장뿐이었습니다 — 셔츠 자리에 러그, 니트 자리에 옷걸이, 청바지 자리에 벨트 버클, 빨간 '화이트 티', 모델 얼굴이 크게 나온 비니, 두 아이템에 같은 사진. **자동 지표 하나(종류 일치)만 보면 품질을 과대평가한다**는 걸 배웠습니다.
- **지금 방식 — 품질 기준을 모두 통과한 사진만 쓰고, 없으면 그림으로**
  1. 상품 사진: FashionCLIP으로 "그 옷만 단색 배경에 놓인 상품 사진"이 사람·얼굴·여러 옷·풍경보다 확률이 높고 0.5 이상
  2. 종류: FashionCLIP 종류 분류의 1등이 정의한 종류
  3. 색: 배경을 지운 뒤 FashionCLIP 색 분류 상위 2개 안에 정의한 색(또는 가까운 색)이 있음
  4. 중복 없음: 다른 아이템이 쓴 사진은 제외
  - 후보는 검색어에 'isolated'를 붙여 30장 받습니다(배경 없는 상품 사진에 많이 붙는 태그). 기준별로 몇 장이 떨어졌는지 기록해 어떤 아이템이 왜 그림이 됐는지 볼 수 있습니다.
  - 마지막 확인은 사람이 사진을 훑어보고, 이상한 건 `--pick 아이템id=사진id`로 바꿉니다.
- 카탈로그 옷은 종류·계절이 정의된 값이라 '확인 필요'를 띄우지 않고, 상황 점수도 미리 계산돼 있어 사진 분석 모델이 없는 서버에서도 추천이 같은 방식으로 돕니다.
- 화면에는 "예시 사진" 표시를 붙이고, 작가 이름과 사진 출처를 보여 줍니다. 사진 파일은 Git에 올리지 않고(스크립트로 다시 받음) 사진 id·작가·주소만 `app/data/catalog.json`에 기록합니다.

**2. 상품 링크로 가져오기** — `app/services/product_link.py`, `app/services/fetch.py`

- 산 옷의 상품 페이지 주소를 넣으면, 쇼핑몰이 링크 미리보기용으로 넣어 둔 `og:image`, `og:title`만 읽습니다. 사용자가 넣은 그 한 페이지만 받으므로 사이트를 통째로 긁는 크롤링과는 다릅니다. 가져온 사진은 그 사용자의 옷장에서만 보입니다.
- 사용자가 아무 주소나 넣을 수 있어서 **SSRF(서버가 내부망에 대신 접속하게 만드는 공격)를 막았습니다.** http/https만 받고, 주소의 IP를 직접 확인해 사설·루프백·클라우드 메타데이터 주소(169.254.169.254)를 거절하고, 리다이렉트도 한 번씩 같은 검사를 다시 하며, 받는 크기에 상한을 둡니다.
- 쇼핑몰이 자동 접속을 막으면(403 등) 그 이유를 그대로 알려 주고, 사진 업로드로 넘어가게 합니다.

## 사진 자동 분류

옷장 앱의 가장 큰 문제는 **사용자가 옷을 하나하나 등록하기 귀찮다**는 점입니다. 그래서 사진을 올리면 입력칸을 AI가 먼저 채우고, 사용자는 틀린 것만 고치게 했습니다 (`app/services/tagger.py`, `POST /api/wardrobe/analyze`).

**최종 방식**

| 항목 | 방법 | 실제 사진 개발용 15벌 | 실제 사진 시험용 9벌 |
|------|------|--------------------|--------------------|
| 종류 | FashionCLIP 제로샷 — 사진 벡터를 "a photo of a jacket" 같은 문장 벡터와 비교 | 93.3% (14/15) | **88.9%** (8/9) |
| 계절 | FashionCLIP 제로샷으로 **두께·소재**를 고른 뒤 계절로 변환 (두꺼운 패딩·울 니트 → 겨울 등), 가방·액세서리는 사계절 | 86.7% (13/15) | **66.7%** (6/9) |
| 색상 | FashionCLIP 제로샷 — "white clothing", "light sky blue clothing" … 20색 | 73.3% (11/15) | **88.9%** (8/9) |
| 스타일 | FashionCLIP 벡터 + 로지스틱 회귀 (상품 사진 4,500장으로 학습, `app/data/`) | 정답 없음 (상품 사진 기준 91.6%) | |

- 라벨마다 문장 여러 개의 벡터를 평균 내 라벨 벡터로 씁니다(프롬프트 앙상블). 문장별 확률을 더하면 문장이 많은 라벨이 유리해져서 평균 방식으로 바꿨습니다.
- 종류는 확률 50% 이상일 때만 채우고, 여러 장을 한 번에 올릴 때는 60% 이상만 자동 분류합니다. 나머지는 '미분류'로 두어 사람이 고릅니다.
- **배경 제거:** rembg(U²-Net)로 옷만 오려 `<원본>_cut.jpg`로 따로 저장하고, 화면에는 이 사진을 보여 줍니다. 분류는 평가한 조건과 같게 원본 사진으로 합니다.
- **자동 이름:** 고른 종류 안에서 세부 종류 문장("a tote bag", "a pair of wide-leg pants" …)과 비교해 "색 + 세부 종류" 이름을 만듭니다. 이 문장들은 종류 분류와 따로 두어, 평가한 분류 정확도에 영향을 주지 않게 했습니다.
- **다시 분석:** 분석 방식을 바꾼 뒤 "↻ 모두 다시 분석"으로 이미 올린 옷을 한 번에 다시 분류하고 배경 제거 사진도 만듭니다.
- torch·transformers·rembg가 없으면 해당 기능만 꺼지고 나머지는 그대로 동작합니다 (`requirements-ml.txt`).

### 1단계: 상품 사진 벤치마크 (`scripts/eval_tagging.py`)

상품 사진 데이터셋(fashion-product-images-small, Kaggle 원본)에서 종류마다 150장씩 900장으로 비교했습니다. (Google Colab T4)

| 항목 | 일반 CLIP 제로샷 | FashionCLIP 제로샷 | FashionCLIP + 로지스틱 회귀 (5-fold) | 무작위로 찍으면 |
|------|-----------------|--------------------|-------------------------------------|----------------|
| 종류 (6개) | 93.7% | **94.6%** | 97.8% | 16.7% |
| 스타일 (캐주얼·포멀·스포티) | 30.6% | 55.8% | **88.9%** | 33.3% |
| 계절 (4개) | 25.6% | 30.8% | **63.0%** | 25.0% |
| 색상 | 평균색 16.7% → k-means(RGB) 36.2% → k-means(Lab + 흰 옷 보정) **47.6%** | | | |

이 결과만 보고 스타일·계절은 로지스틱 회귀를 학습해 쓰고(`scripts/train_probe.py`, 따로 떼어 둔 20%에서 스타일 91.6%, 계절 64.2%), 색상은 k-means를 썼습니다.

### 2단계: 실제 옷장 사진에서는 무너졌다

직접 찍은 옷 6벌을 올려 보니 종류는 다 맞았지만, **계절은 니트·패딩까지 대부분 '여름'으로, 색은 흰 재킷이 '그레이'로** 나왔습니다. 그래서 내 옷 사진에 정답을 달아 개발용 평가셋을 만들고(`eval_photos/`, 15벌, 개인 사진이라 저장소에는 넣지 않음) 원인을 찾았습니다.

| 문제 | 원인 | 바꾼 방식 |
|------|------|-----------|
| 계절이 거의 다 '여름' | 학습 데이터가 인도 쇼핑몰 상품이라 "Summer" 라벨이 대부분이고 겨울옷이 드묾. 상품 사진끼리 잰 64%가 한국 옷장에는 통하지 않음 (**학습 데이터와 실제 사용 환경의 차이**) | 데이터셋 라벨 대신 눈에 보이는 **두께·소재**를 제로샷으로 판단 |
| 색이 배경에 끌려감 | k-means는 "사진 가장자리 = 배경"을 가정. 실제 사진에는 책상·벽·손·옷걸이가 함께 찍힘 | CLIP 제로샷으로 색 판단 (사진 속 옷에 주목해 배경에 덜 흔들림), 아이보리·라벤더 등 연한 색 추가 |

| 실제 사진 개발용 15벌 | 이전 방식 | 바꾼 방식 |
|---------------|----------|-----------|
| 계절 | 학습한 분류기 (6벌 중 대부분 '여름') | 두께 제로샷 **86.7%** |
| 색상 | 평균색 6.7%, k-means 13.3% | CLIP 제로샷 **73.3%** |
| 종류 | — | 제로샷 **93.3%** |

### 3단계: 처음 보는 사진으로 다시 확인 (시험용)

개발용 15벌은 결과를 보면서 방식을 고쳤기 때문에, 그 점수만 믿으면 "시험 문제를 보고 공부한" 셈이 됩니다. 그래서 **방식을 다 정한 뒤 처음 보는 사진 9장**(여름옷 6벌, 가방 3개)을 따로 찍어 한 번만 재고, 결과를 고치지 않고 그대로 적었습니다.

- **색상 88.9%, 종류 88.9%** 로 개발용과 비슷하거나 더 좋았습니다. 틀린 것은 흰 반바지 → 베이지, 흰 린넨 셔츠 → 하의(접어 놓은 셔츠) 하나씩입니다. 같은 사진에서 k-means는 색을 22.2%만 맞혀, CLIP으로 바꾼 결정이 처음 보는 사진에서도 유지됐습니다.
- **계절은 66.7%로 떨어졌습니다.** 틀린 3벌은 모두 여름옷인데 가을로 본 경우(반팔 시스루 가디건, 얇은 트레이닝 바지, 얇은 와이드 바지)입니다. 개발용에서는 반대로 두꺼운 치마 2벌을 여름으로 봤습니다. 둘을 합쳐 보면 CLIP이 **소재 두께보다 옷의 길이·모양**(짧으면 여름, 길면 가을)으로 판단하는 경향이 있습니다. 개발용에서 소재 문장(울·골지·린넨)을 보강해 봤지만 치마 2벌은 고쳐지지 않았습니다.
- 개발용과 시험용을 합쳐 **종류별로 나눠 보면** 차이가 뚜렷합니다. 상의·아우터는 13벌 중 12벌을 맞혔고 가방은 규칙으로 3벌 모두 맞았지만, **하의는 8벌 중 4벌**(두꺼운 치마 → 여름, 얇은 바지 → 가을)이었습니다. 치마·바지는 길이·모양이 계절과 거의 상관이 없고, 원단 두께는 사진에 잘 드러나지 않기 때문으로 봅니다. (`eval_tagging.py --photos`가 이 종류별 결과를 함께 출력합니다.)
- 그래서 프롬프트를 더 고쳐 평가셋에 맞추는 대신 **하의만 AI 계절을 "확인 필요"로 둡니다.** 옷장 카드에 계절 버튼이 뜨고(AI 추측은 점선), 한 번 누르면 확정됩니다. 사용자가 고른 계절은 `season_by_user`로 저장해 **"모두 다시 분석"을 해도 덮어쓰지 않습니다.** 정확도가 높은 상의·아우터는 묻지 않아 확인할 옷이 줄어듭니다.
- 계절이 틀려도 추천 점수에서 봄·가을은 같은 간절기로 묶이므로, 영향이 큰 것은 여름↔겨울을 혼동하는 경우입니다.

**배운 점**
- 상품 사진 벤치마크에서 64%였던 계절 분류기는 실제 옷장 사진에서 무너졌습니다. **학습 데이터와 실제 사용 환경이 다르면 점수가 그대로 통하지 않습니다.**
- 실제 사진으로 만든 작은 평가셋이 방향을 바꾸는 근거가 됐습니다. 그리고 개발용과 시험용을 나눠야 개선이 진짜인지 알 수 있었습니다.
- 표본이 작아(개발용 15벌, 시험용 9벌) 한 벌 차이가 6.7~11.1%p입니다. 사진을 더 모아 계속 재 볼 계획입니다. 스타일은 실제 사진에 정답을 달지 못해 평가하지 않았습니다.

> 상품 데이터셋은 저장소에 넣지 않고 실행할 때 내려받습니다. Hugging Face 복사본에는 라이선스 표시가 없어 평가·학습에만 사용했습니다.

## 프로토타입에서 바꾼 점

처음 버전은 HTML 파일 하나(약 1,500줄)로 만든 프로토타입이었습니다. 실제 서비스 구조로 옮기면서 다음 문제를 고쳤습니다.

| 문제 (이전) | 바꾼 방식 (지금) |
|-------------|------------------|
| Groq·기상청 API 키를 사용자가 브라우저에 입력하고, 브라우저가 외부 API를 직접 호출 → 키 노출 | 키는 서버 환경변수(.env)에만 두고, 브라우저는 우리 서버 API만 호출 |
| 회원 비밀번호를 브라우저 localStorage에 원문으로 저장 | PBKDF2-SHA256(사용자별 salt, 20만 회) 해시만 DB에 저장, 로그인은 JWT |
| 옷 사진을 localStorage에 저장 → 약 5MB에서 가득 참, 다른 기기에서 안 보임 | 브라우저에서 800px로 줄여 업로드, 서버 폴더에 저장하고 DB에는 파일 이름만 |
| 추천 결과에 나온 옷을 바로 "입은 옷"으로 기록 | "이 코디로 결정"을 눌렀을 때만 기록 |
| 체감온도를 `기온 − 풍속`으로 계산 | 기상청 겨울철 체감온도 공식 적용 (기온 10도 이하, 풍속 4.8km/h 이상일 때) |
| 지원이 끝난 모델(llama-3.3-70b-versatile)로 추천이 실패 | 모델 이름을 설정 한 곳(`GROQ_MODEL`)에서 관리, openai/gpt-oss-120b 사용 |
| 동작하지 않는 카카오·구글·애플 로그인 버튼 | 제거 (구현한 기능만 화면에 표시) |
| 없는 폴더(NestJS 모노레포)를 가리키는 package.json, docker-compose.yml | 제거. 초기 기획서는 `docs/planning.md`에 보관 |

## API

서버를 켜고 `http://127.0.0.1:8000/docs`에 들어가면 모든 API를 바로 호출해 볼 수 있습니다.

| 메서드 | 경로 | 설명 |
|--------|------|------|
| POST | `/api/auth/signup` | 회원가입 → 토큰 |
| POST | `/api/auth/login` | 로그인 → 토큰 |
| GET | `/api/me` | 내 정보 |
| PUT | `/api/me/profile` | 프로필 저장 |
| GET | `/api/wardrobe` | 내 옷 목록 |
| POST | `/api/wardrobe` | 옷 등록 (multipart, 사진 선택) |
| PATCH | `/api/wardrobe/{id}` | 옷 정보 수정 |
| DELETE | `/api/wardrobe/{id}` | 옷 삭제 (사진 파일도 삭제) |
| GET | `/api/wardrobe/catalog` | 기본 옷 목록 (사진·작가·출처) |
| POST | `/api/wardrobe/from-catalog` | 고른 기본 옷을 한꺼번에 옷장에 넣기 |
| POST | `/api/wardrobe/import-link` | 상품 주소 → 대표 사진·상품명 (저장 안 함) |
| POST | `/api/wardrobe/analyze` | 사진 분석만 (저장 안 함) → 종류·색·계절·스타일과 확신도 |
| POST | `/api/wardrobe/wear` | 오늘 입은 옷 기록 |
| GET | `/api/weather?city=서울` 또는 `?lat=&lon=` | 지금 날씨 |
| POST | `/api/recommend` | 상위 코디 3개 (항목별 점수·이유·LLM 설명) |
| POST | `/api/recommend/sample` | 평가용 코디 (점수 상위·중간·하위에서 섞어 뽑음) |
| POST | `/api/recommend/feedback` | 코디 평가 저장 (👍 1 / 👎 -1) |

- 입력값은 Pydantic으로 검사합니다(정해진 기분·상황·카테고리만 허용, 비밀번호 8자 이상 등). 틀리면 422를 돌려줍니다.
- 남의 옷을 수정·삭제하려 하면 403이 아니라 404를 돌려줍니다. 다른 사람 옷의 존재 여부를 알 수 없게 하기 위해서예요.
- 로그인할 때 없는 이메일과 틀린 비밀번호에 같은 메시지를 줘서, 가입 여부를 알 수 없게 했습니다.
- 서버에 키가 없으면 503, 외부 API가 실패하면 502를 돌려줍니다. 화면은 이 상태 코드에 맞춰 안내합니다(날씨 → 직접 입력 등).
- 같은 격자·같은 발표 시각의 날씨는 30분 동안 서버 메모리에 저장해 기상청 호출을 줄입니다.

```bash
python scripts/build_catalog.py   # (선택) 기본 옷 44종 사진 받기 — PIXABAY_API_KEY 필요
uvicorn app.main:app --reload # http://127.0.0.1:8000
```

## 테스트

```bash
python -m pytest
```

Groq와 기상청은 가짜 함수로 바꾸고, 테스트마다 빈 임시 DB를 씁니다.

- `test_auth.py`: 가입·로그인, 비밀번호가 원문으로 저장되지 않는지, 토큰 없는 요청 거절
- `test_wardrobe.py`: 등록·수정·삭제, 사진 형식·용량 제한, **다른 사용자의 옷에 접근할 수 없는지**
- `test_outfits.py`: 색 조합 규칙(포인트 1색·톤온톤·청바지·블랙+네이비), 추우면 아우터 필수·더우면 제외, 여름에 겨울옷이 밀리는지, **사진 분석 상황 점수로 출근엔 셔츠·운동엔 트레이닝복**, 최근 입은 옷 감점과 겹치지 않는 3개
- `test_recommend.py`: 내 옷으로만 코디를 만드는지, LLM이 실패해도 코디는 보여 주는지, 평가 저장과 남의 옷 평가 거절
- `test_scoring.py`, `test_eval_outfits.py`: 기온 → 계절 규칙, AUC·leave-one-out 계산
- `test_weather.py`: 위경도 → 기상청 격자 변환(서울 60,127 / 부산 98,76), 발표 시각 계산, 체감온도, Encoding 키가 두 번 인코딩되지 않는지, 기상청 키가 없을 때 Open-Meteo로 바뀌는지
- `test_import.py`: 내부망·이상한 주소 차단(127.0.0.1, 192.168.x.x, 169.254.169.254, file://), 상품 페이지에서 사진·상품명 읽기, 기본 옷 넣기(중복 제거, 상황 점수 복사, 계절 확인 생략)
- `test_tagger.py`: 배경을 빼고 옷 색을 맞히는지, 분석 API가 저장 없이 결과만 주는지, 모델이 없을 때 503, **사용자가 고친 하의 계절·종류를 다시 분석이 덮어쓰지 않는지**, 예전 DB 파일에 새 열이 추가되는지

## 한계와 다음 단계

- 원피스·이너웨어 같은 카테고리는 아직 없습니다.
- 기본 옷 카탈로그는 색이 정해져 있어(예: 네이비 니트) 가진 옷과 색이 다르면 비슷한 걸 고르거나 직접 등록해야 합니다.
- 상품 링크는 쇼핑몰이 자동 접속을 막거나 화면을 자바스크립트로만 그리면 실패할 수 있습니다.
- 로그인 토큰은 브라우저 localStorage에 저장합니다. 서비스로 운영한다면 HttpOnly 쿠키로 바꾸는 게 더 안전합니다.
- 사진은 서버 폴더에 무작위 파일 이름으로 저장하고, 주소를 알면 볼 수 있습니다. 운영 환경에서는 S3 같은 저장소와 서명된 URL을 쓰는 게 맞습니다.
- 색 조합 규칙은 일반적인 코디 공식이라 개인 취향과 다를 수 있습니다. 평가가 충분히 모이면 학습한 가중치를 사용자별로 적용해 볼 계획입니다.
- **옷끼리 격 맞추기가 없습니다.** 지금 점수는 옷을 하나씩 보고 날씨·상황·색만 따져서, 색만 맞으면 니트에 트레이닝 바지 같은 조합도 점수가 높을 수 있습니다. 옷마다 격식 정도(1~5)를 사진으로 매기고 한 코디 안의 차이에 감점하는 것이 다음 개선입니다.
- 핏·실루엣(오버핏 상의 + 슬림 하의 등)은 아직 반영하지 않았습니다.
- 도시 검색은 미리 넣어 둔 도시 목록만 됩니다(현재 위치는 어디서나 됨). Open-Meteo 지명 검색을 붙이면 아무 도시나 찾을 수 있습니다.
- **"다음에 살 옷" 추천**: 기본 옷을 하나씩 내 옷장에 넣어 본다고 가정해 괜찮은 코디가 몇 개 늘어나는지 계산하면, 쇼핑몰이 못 하는 "내 옷장 기준 쇼핑 추천"이 됩니다. 아이디어 단계입니다.
- 배포(Docker + Render 등)와 커뮤니티 기능은 아직 하지 않았습니다.
